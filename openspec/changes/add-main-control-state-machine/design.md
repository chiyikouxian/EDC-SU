## Context

用户本人负责硬件 B，当前使用 MSPM0 开发板，仓库已有 `empty/` 空白工程。视觉平台已确认是树莓派 4B + USB 摄像头 + Python/OpenCV，通过 UART 与 MSPM0 通信。

本阶段目标不是直接完成整车，而是先建立主控流程骨架，使后续视觉、底盘和云台能够按统一接口逐步接入。

## Goals / Non-Goals

Goals:
- 在 MSPM0 工程中形成清晰的状态机结构。
- 明确基础行进、基础导航、发挥导航三种模式的状态流。
- 明确主控与视觉、底盘、云台、蜂鸣器的接口边界。
- 为 Claude 后续执行提供严格范围，避免擅自扩展功能。

Non-Goals:
- 不在本阶段调通真实底盘循迹。
- 不在本阶段完成 OpenCV 视觉识别。
- 不在本阶段完成最终引脚表和 PCB 设计。
- 不在本阶段追求速度优化。

## Decisions

- Decision: 主控流程使用显式状态机。
  - Reason: 比赛流程强依赖时序，显式状态比散落的 `if`/`delay` 更容易审查和联调。

- Decision: 视觉结果通过结构化 UART 帧传输。
  - Reason: 树莓派和 MSPM0 分属两个系统，帧协议可降低串口乱码和半包带来的误触发风险。

- Decision: 本阶段底盘和云台先定义接口，允许用 stub 占位。
  - Reason: 硬件 A 和视觉模块可能尚未完成，硬件 B 应先搭好可集成框架。

- Decision: 蜂鸣器流程纳入状态机，不用长阻塞延时堆叠。
  - Reason: 后续需要同时处理串口、按键、云台和电机锁，阻塞式流程会降低可控性。

- Decision: 模式选择使用单按键循环切换。
  - Reason: 用户已确认初始上电为基础行进模式，每按下一次按键依次切换到基础导航、发挥导航，再循环回基础行进。

- Decision: 蜂鸣器使用低电平触发有源蜂鸣器。
  - Reason: 用户已确认硬件类型，因此蜂鸣器抽象层应以低电平为响、高电平为关的语义实现。

- Decision: 本阶段允许先实现可编译状态机骨架和接口 stub，不绑定真实引脚。
  - Reason: 用户已确认可以先搭框架；最终引脚连接表和真实外设接入可作为后续 change 处理。

## Risks / Trade-offs

- Risk: 没有最终引脚表，代码可能只能做结构和接口，不能直接上板运行。
  - Mitigation: 将引脚配置保持在 SysConfig 或硬件抽象层，真实引脚由后续 change 确认。

- Risk: 视觉 UART 协议如果现在定死，后续视觉端可能需要调整。
  - Mitigation: 本阶段定义最小协议，保留 `VALID` 和 `NONE` 状态，避免过早加入复杂字段。

- Risk: 底盘路径表尚未实测，状态机无法判断真实到点。
  - Mitigation: 使用 `TARGET_REACHED` 抽象状态，具体触发由硬件 A 后续实现。
